## Architecture boundaries (non-negotiable)

Modules: `device/`, `capture/`, `hid/`, `rtc/`, `web/`. Entry point: `main.rs`. The WebRTC module is named `rtc`, not `webrtc` — a module called `webrtc` would shadow the `webrtc` crate it depends on. Target design mirrors the browser device/track model (`mediaDevices`/`getUserMedia`/`MediaStreamTrack`/`EventTarget`).

- Each module owns its own config, validation, state, and I/O — including its own device path, read from its own config. Modules interact ONLY through each other's exposed APIs (traits). Never import another module's internals.
- No shared utils, no shared config, no shared state. Duplicate code instead.
- Two ways to communicate, nothing else: **events** — callback subscriptions (`EventEmitter`/`add_event_listener`, `EventTarget`-style), dispatched per-listener via `tokio::spawn` fire-and-forget, auto-deregistered on `Subscription` drop. NOT a `watch` channel, NOT Rayon (rejected: these callbacks are async I/O, not CPU-heavy). And **commands** — an async API call returning a typed result.
- `main.rs` implements nothing. It constructs `rtc` and `web` only, wires them, and starts them. `rtc` builds its own `capture` and `hid` dependencies as part of being built. Each module spawns whatever tasks it owns — `capture`'s `Device` presence task, `hid`'s own device and drain worker. No domain logic, no config values, no path strings.
- `device/` is the ONLY module that knows OS device paths. It is a generic `Device<D: DeviceDriver>` core (presence detection, probe-once-on-appear, `devicechange` events) plus per-kind drivers (`CaptureDriver`, `Ch9329Driver`, future UART) — the drivers live here because they're the only code that touches a path or does a raw OS open. `Device::open()` is the sole path-touching call; it hands back an OS handle, never a path. One instance per physical device; each reads its own path from its own config.
- `capture/` is the encode pipeline (`getUserMedia`). `CaptureCard` holds a `CaptureDevice` but never subscribes to it, only opens it. `request_stream() -> Result<CaptureStream, OpenError>` genuinely either fails (device absent, or the open itself failed) or returns a live per-consumer stream (= `MediaStreamTrack`) with a live-guard — no separate presence pre-check. Its `ended` event is only for a pass that opened fine and dies later (a mid-read error), never for the open failing (that's the `Err` above) and never from a device-presence subscription. `device()` hands the same `CaptureDevice` handle back for direct use elsewhere (see `rtc/`). Encoder runs iff live handles > 0. Owns capture settings in memory. Knows no path; talks to no other module.
- `hid/` holds a `Ch9329Device` and drains an internal queue to the CH9329 in received order via one worker — purely command-driven, the same as `capture`: for each command it opens the port (or reuses one already open) through the Device API and writes; either it works or it logs the error and moves to the next command. No presence subscription of its own any more, not even internally — a stale command isn't worth holding for a later replug anyway. Exposes "send a message", mouse mode, and `device()` (the same `Ch9329Device` handle, for direct use elsewhere).
- `rtc/` owns peer sessions and offer→answer, and constructs its own `capture`/`hid` dependencies as part of being built. It is now the only module that subscribes to device presence at all — it keeps its own `CaptureDevice`/`Ch9329Device` handles, clones obtained from `capture.device()`/`hid.device()`, not a second `Device::spawn()`. On a presence-present event (the event itself already carries the probed capture info — resolutions, frame rates — so `rtc` never calls a separate probe), it updates `DeviceState` and pushes it to every session's control channel — it does **not** call `capture.request_stream()` here, since a track nobody can receive isn't worth having. Every session that wants video calls `capture.request_stream()` for itself, once, when it reaches `Connected` and the card is present — `rtc` doesn't cache or hand out one shared stream object; `capture`'s own live-consumer count is what guarantees only one real device open/encode pass happens no matter how many sessions call it. This matters for correctness, not just simplicity: each stream has its own private read cursor into the frame feed, so two sessions sharing the literal same stream object would each only see every *other* frame. When a session stops holding its track, it drops its own stream; once every session sharing that pass has done the same, `capture`'s live count hits zero and the encoder stops even though the card may still be plugged in, so "no session, no encoder" holds regardless of presence. On presence-absent, or on a session's own stream `ended` event (the pass dying after a successful start), each session that currently holds a track removes it and renegotiates on its own — whichever of the two fires first for that session, the other is a no-op. `rtc` reports HID-available from its own `Ch9329Device` handle. Peer input goes straight to the `hid/` API regardless of presence — a failed send there is `hid`'s own concern. Never runs HTTP, touches paths, or implements capture/HID logic.
- `web/` implements nothing. It serves the page and signaling endpoints; every handler parses the request and calls the `rtc/` API. Never generates an answer, holds state, or talks to `device/`/`capture/`/`hid/`.

Allowed dependency edges (nothing else): `capture→device`, `hid→device`, `rtc→capture`, `rtc→hid`, `rtc→device`, `web→rtc`.

Before adding code, ask: which module owns this? Put it there. If it needs a new edge, or a device path outside `device/` — stop and update the architecture doc first, then ask. Full rationale: @docs/ARCHITECTURE.md
